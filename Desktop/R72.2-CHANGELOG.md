# TOR POS R72.2 – Cloud Redirect Hotfix

## Problem
R72.1 SafetyTests reached the Cloud redirect security test and failed:

`FAIL: Redirect response is rejected without forwarding credentials`

The redirect itself was NOT followed. `TorCloudSyncService` already used:

`HttpClientHandler { AllowAutoRedirect = false }`

The actual problem was error classification:

1. Test server returned HTTP 302 with an empty body.
2. RequestAsync tried to parse the empty body as JSON before evaluating HTTP status.
3. JSON parsing threw InvalidDataException.
4. SyncOnceAsync intentionally hides non-approved exception detail and stored the generic
   `Cloud nicht bestätigt...` status.
5. The safety test therefore could not see `HTTP 302`.

## Fix
RequestAsync now evaluates HTTP status first.

For every non-2xx response:
- no success JSON is required,
- redirect is not followed,
- safe status code is retained, e.g. `Cloud HTTP 302`,
- arbitrary HTML/text response bodies are not shown,
- an optional JSON `error` field may be included up to 500 chars.

Only successful 2xx responses are parsed as Cloud acknowledgement JSON.

## Additional redirect hardening
The older/direct `TorCloudConnectionService.PingAsync` path previously created a
default HttpClient, whose handler may automatically follow redirects.

R72.2 explicitly sets:
`AllowAutoRedirect = false`

there too, so X-Device-Code / X-Device-Token are never intentionally carried into
a redirected request by TOR POS.

## Test
The existing redirect check still counts as one Safety Check, but now additionally
verifies that exactly one HTTP request occurred.

Total target remains:
`ALL 298 CHECKS PASSED`

## Notes
The remaining 3 Avalonia AVLN3001 warnings are compile warnings, not this failure.
They are caused by DI/factory-created windows without public parameterless
constructors and are intentionally not changed in this hotfix.
